# go-yomikae の設計

go-yomikae は、日本語 TTS (IrodoriTTS) に渡すテキストから英字を取り除き、カナの読みに置き換える。
Go のライブラリ、CLI、OpenAI 互換のリバースプロキシの三つの形で使える。

最優先の目標は、出力に英字を一文字も残さないことだ。IrodoriTTS は日英混在文で英単語の前後の日本語まで崩す。
そのため、不自然なカナを出すほうが英字を残すよりよい。読みの精度は二番目の目標とする。

この文書は設計の理由を説明する。使い方は [README](../README.md) に、重みの入手手順は
[models.md](models.md) にある。

## 調査の結果

### speech.cpp の /v1/audio/speech

[nyosegawa/speech.cpp](https://github.com/nyosegawa/speech.cpp) の commit 49f022a を読んだ。

- リクエストは JSON オブジェクトで、`input` (必須の文字列)、`model`、`voice`、`response_format`
  (`wav` か `pcm`)、`stream_format` (`audio` か `sse`)、`speed`、`instructions` と、
  モデルのオプション (`seed`、`steps` など) を持つ。知らないメンバーは 400 で拒否される
  (`tools/server/openai-api.cpp` の `read_speech_request`)。
  したがってプロキシはメンバーを足しても消してもいけない。
- `stream_format: "sse"` のとき、応答は `Content-Type: text/event-stream` のチャンク転送になる。
  イベントは `data: {"type":"speech.audio.delta","audio":"<base64 PCM>"}` を音声のチャンクごとに送り、
  最後に `data: {"type":"speech.audio.done","seed":42,"samples":134400,"stop":"complete"}` を送る。
  失敗は `data: {"type":"error","error":{...}}` になる。`event:` 行はない。
- `response_format: "pcm"` だけでも、音声は生成と同時にチャンクで流れる。
  プロキシは SSE に限らず、すべての応答を逐次転送する必要がある。
- `X-Sample-Rate` と `X-Speech-Seed` は応答ヘッダで返る。
- ほかのエンドポイントは `GET /v1/models`、`POST /v1/audio/transcriptions`、WebSocket の `GET /v1/realtime`
  などで、プロキシはそのまま転送する。

### IrodoriTTS が英字として受け取る文字

IrodoriTTS の公式ランタイムも speech.cpp も、テキストに NFKC を掛けてから SentencePiece (Unigram) で分割する
(`irodori_tts/text_normalization.py`、speech.cpp の `src/families/irodori-tts/text-normalizer.h`)。
ここから二つのことが分かる。

- 全角英字 `ＰＤＦ`、数学用英字 `𝙈𝙮`、互換文字 `㎏`、`™`、`℃`、`Ⅲ` は、モデルには ASCII 英字として届く。
  変換の対象は「NFKC の結果に英字を含む文字」まで広げる必要がある。zenn-content の記事にも `𝙈𝙮` が出てきた。
- 語彙 (102,400 語) はギリシャ文字、キリル文字、ハングル、アクセント付き英字を一文字の語として持っている。
  バイトに分解されることはないので、トークナイザーの段階では英字と差がない。破綻するかは音声で確かめる必要がある。

音声でも確かめた。日本語の文 8 本の中ほどに一語ずつ差し込み、IrodoriTTS v4.1-Small-MF で 3 シードずつ合成し、
Qwen3-ASR 0.6B で書き起こした (`eval/asr_eval.py`、入力は `eval/charset-probe.tsv`)。
差し込んだ語の前後の日本語が書き起こしに残る割合 (LCS 再現率) は次のとおりだった。

| 差し込んだ語 | 平均再現率 | 0.8 未満の割合 | 差し込んだ語の聞こえ方 (シード 1 の例) |
| --- | --- | --- | --- |
| なし (対照) | 0.965 | 0% | |
| `アルファ` | 0.982 | 0% | アルファ |
| `update` | 0.989 | 0% | アップデート |
| `API` | 0.989 | 0% | API |
| `GitHub` | 0.982 | 0% | ギットハブ |
| `α` | 0.985 | 0% | あー、ああ |
| `λόγος` | 0.986 | 0% | ロゴス、ロガオス |
| `Привет` | 0.987 | 0% | フィリデット、V B ペット |
| `café` | 0.969 | 0% | ケフレイ、ケフェ |
| `안녕` | 0.984 | 0% | 大、愛し |

短い文に一語を差し込むだけでは、どの文字種でも前後の日本語は崩れなかった。破綻は、英字のスパンが多い文や
長い文で起きると考えられる (推測)。二次指標はこの理由から、プローブではなく実コーパスの文で測る。

一方、差し込んだ語の読みは文字種で差が出た。ギリシャ文字一文字の `α` は「アルファ」ではなく「あー」と読まれた。
キリル文字とハングルも意味のない音になった。

音声での確認結果から決めた対象は「[対象の文字集合](#対象の文字集合)」に書いた。

### 英字スパンの種類と頻度

実際に TTS へ流れる文に近いコーパスとして二つを使った。

- `tenkoh/zenn-content` の記事 48 本 (技術ブログ)。コードブロックと front matter を除いた、日本語を含む行。
- `testdata/corpus/synthetic-llm.txt`。LLM の応答を模して 13 分野で書いた合成コーパス。

Claude Code の会話記録も候補にしたが、個人データを含むので使っていない。

次の表は、空白と句読点で区切ったスパンを形で分けた数だ (調査用の簡易スクリプトで数えた。
実装後は `yomikae stats` で同じ集計を出せる)。

| 種類 | zenn (2,993 スパン) | 合成 (647 スパン) | 例 |
| --- | --- | --- | --- |
| 先頭大文字の語 | 28.8% | 23.5% | Go、Python、Google |
| 小文字の語 | 26.4% | 11.1% | install、git、npm |
| 頭字語 | 16.8% | 25.8% | AWS、API、GDP |
| camelCase、大小混在 | 8.8% | 6.5% | GitHub、iPhone、useState |
| ドット区切り | 6.4% | 1.1% | go.mod、config.yaml |
| 英数混在 | 4.3% | 16.7% | S3、CO2、2.4GHz、4K |
| パス、スラッシュ | 2.5% | 2.0% | CI/CD、/var/log/app |
| ハイフン区切り | 1.6% | 2.5% | Wi-Fi、USB-C |
| 一文字 | 1.5% | 5.9% | A、x |
| URL、メール | 1.3% | 0.6% | |
| snake_case | 1.2% | 0.8% | DATABASE_URL |
| ASCII 以外の英字 | 0.2% | 3.6% | café、ＰＤＦ、𝙈𝙮、90℃ |

zenn では 61%、合成では 70% の行が英字を含む。日本語に直に接するスパンは zenn で 49%、合成で 81% ある。

この分布から、手間を掛ける場所を次のように決めた。

- 語 (先頭大文字と小文字で 40 から 55%) は e2k に任せ、固有名詞の読みが外れるものを分野別辞書で直す。
- 頭字語 (17 から 26%) は文字読みを既定にする。文字読みは機械的に正しく読めるので、単語読みの頭字語だけを辞書に書く。
- camelCase は大文字小文字の境目で分けると、`GitHub` がギット・ハブ、`iPhone` がアイ・フォンになる。分割の規則に手間を掛ける。
- 英数混在 (合成で 17%) の多くは単位 (`10g`、`2.4GHz`) だ。単位の辞書を別に持つ。
- URL、パス、snake_case は合わせて 5% 前後なので、記号で区切って部品ごとに読むだけにする。記号は残す。

## 処理の流れ

```text
入力
 └─ 1. 辞書照合: 全辞書の候補を集め、最左・最長・優先度で選ぶ。選んだ範囲は保護する
 └─ 2. スパン抽出: 保護範囲の外で、英字を含むトークンを切り出す
 └─ 3. 分割と分類: トークンを部品 (piece) に分け、部品ごとに word / acronym / letter に分ける
 └─ 4. 読みの生成: 部品の分類ごとのフォールバック連鎖で、必ずカナを返す
出力 (英字ゼロ) と追跡情報 (Rewrite の列)
```

各段階は入力の元の文字列のバイト範囲で結果を返す。英字を含まない部分には一切触れないので、
英字を含まない入力は同じバイト列のまま返る。不正な UTF-8 もそのまま残る。

### 対象の文字集合

ルーン `r` は次のどれかを満たすとき「英字」とする。判定は `internal/script` の一つの関数にまとめる。

1. Unicode の Latin 文字で、かつ文字 (`unicode.Is(unicode.Latin, r) && unicode.IsLetter(r)`)。
   ASCII、全角、アクセント付き (`é`、`ß`、`ø`) を含む。
2. `norm.NFKC` を掛けた結果に 1 の文字を含む (`㎏`、`™`、`℃`、`Ⅲ`、`𝙈`、`ⓐ`、`ﬁ`)。
3. ギリシャ文字 (`unicode.Greek` の文字と、NFKC でギリシャ文字になる `µ` などの互換文字)。
   IrodoriTTS は `α` を「あー」と読んだ。理工系の LLM 出力に出てくるうえ、読み表 (アルファ、ベータなど) で
   文字ごとに読めば済むので、手間が小さい。

英字に続く結合文字 (`e` + U+0301) は同じスパンに含め、英字と一緒に消す。消さないとカナに結合文字が残る。

キリル文字とハングルは対象外とする。読みは崩れたが前後の日本語は崩れなかったこと、
二つのコーパスでの出現が 0 件だったことが理由だ。
対象を広げるときは `internal/script` の判定と読み表を足す。

### 1. 辞書照合

辞書は TOML ファイルで書く。形式は「[分野別辞書](#分野別辞書)」で説明する。

照合は、元の文字列から作る「照合用ビュー」の上で行う。ビューはルーンごとに NFKC を掛けた文字列で、
ビューの各バイトが元の文字列のどのルーンから来たかを表で持つ。これで `ＧｉｔＨｕｂ` も `GitHub` の項目に当たる。
ビュー上の一致は、元のルーン境界に揃うものだけを採る (`㎏` の展開 `kg` の途中から始まる一致は採らない)。

候補の集め方は次のとおり。

- リテラル項目は、折り畳んだキー (既定は小文字化) のトライで、各位置から始まる一致を全部集める。
  キーの先頭が英字なら一致の直前のルーンが英字でないこと、キーの末尾が英字なら直後のルーンが英字でないことを求める。
  `Go` の項目が `Google` の中に当たらないようにするためだ。数字との隣接は許す (`Go1.18` の `Go` には当たる)。
  先頭が記号のキーは英字の直後でも当たる (`.py` は `main.py` の `.py` に当たる)。
- 正規表現項目は `FindAllSubmatchIndex` で一致を集める。英字を含まない一致は捨てる。
  英字を含まない文を変えない、という性質を辞書が壊さないようにするためだ。

候補の選び方は「最左、次に最長、次に優先度、次に定義順」とする。候補をこの順に並べ、
直前に採った範囲と重ならないものを採っていく。

- 優先度は辞書ファイルの指定順で、後に指定したファイルほど高い。同梱辞書を先に読み、
  利用者の辞書を後に読むので、同じキーを書けば利用者の読みが勝つ。
- 長さを優先度より先に見る。同梱辞書の `GitHub Actions` は、利用者辞書の `GitHub` より長いので勝つ。
  利用者が `GitHub Actions` の読みを変えたいときは、そのキーを自分の辞書に書く。
  優先度を先に見る方式は、短い利用者項目が同梱の複合語を壊すので採らない。

正規表現の置換は `$1` などのキャプチャを使える。キャプチャした部分に英字が残ることがあるので、
置換の前に各キャプチャを 2 から 4 の段階で変換してから展開する。置換テンプレートのリテラル部分は
読み込み時に英字を含まないことを検査済みなので、展開結果は英字を含まない。
キャプチャの変換も、元の文字列のバイト範囲を持つ Rewrite として追跡情報に出る。

### 2. スパン抽出

保護範囲の外を一文字ずつ見て、ルーンを次の種類に分ける。

| 種類 | 中身 |
| --- | --- |
| `L` | 英字 (前節の定義) と、その後の結合文字 |
| `D` | 数字 (`unicode.IsDigit`、全角数字) |
| `Q` | 英字に挟まれたアポストロフィ (`'`、`’`) |
| `O` | それ以外 |

`L`、`D`、`Q` の最長の連続をトークンとし、英字を一つ以上含むものだけを変換する。
記号 (`.`、`_`、`-`、`/`、`:`) と空白はトークンを区切り、出力にそのまま残る。

トークンの外側には、表示とデバッグのためだけに「スパン」の種類を付ける。空白と日本語で区切った、
記号を含む連続 (`config.yaml`、`https://go.dev/doc`) を一つのスパンと見て、
`url`、`path`、`identifier` (snake_case、kebab-case、ドット区切り、camelCase)、`alnum`、`acronym`、`word`、
`letter` に分ける。日本語と直に接するスパンには `mixed` の印を付ける。スパンの種類は読みを変えない。
読みを変えるのは次の段階の部品の分類だけだ。

### 3. 分割と分類

トークンを次の境界で部品に分ける。

- 英字と数字の境目。`mp3` は `mp` と `3`、`H2O` は `H`、`2`、`O`、`v1.2` は `v`、`1`、`.`、`2`、
  `5G` は `5` と `G`、`i7-14700K` は `i`、`7`、`-`、`14700`、`K` になる。数字はそのまま残る。
- 小文字から大文字への境目。`getUserById` は `get`、`User`、`By`、`Id` になる。
- 大文字の連続の後に大文字と小文字が続く境目。`HTTPServer` は `HTTP` と `Server` になる。
  `iPhone` は `i` と `Phone`、`DynamoDB` は `Dynamo` と `DB`、`macOS` は `mac` と `OS` になる。

部品は次の三つに分ける。

| 分類 | 条件 | 例 |
| --- | --- | --- |
| `letter` | 英字が一文字 | `H`、`x`、`α` |
| `acronym` | 英字が二文字以上で、すべて大文字 | `API`、`OS`、`DB` |
| `word` | それ以外 | `update`、`Phone`、`get`、`café` |

### 4. 読みの生成

分類ごとに生成器の連鎖を表で持つ。連鎖は前から試し、カナを返した最初の生成器の結果を使う。
生成器が英字を含む文字列や空文字列を返したら、失敗として次へ進む。

| 分類 | 連鎖 |
| --- | --- |
| `word` | 発音判定 → e2k (C2K) → 文字読み |
| `acronym` | 文字読み |
| `letter` | 文字読み |

- **発音判定** は本家 e2k の NGram に当たる。`word` の部品だけに使い、「単語として読むか、
  一文字ずつ読むか」を決める。発音できないと判定したら e2k を飛ばして文字読みにする (`mp`、`npm`、`pkg`)。
  既定では同梱した本家の NGram データを使い、本家と同じ線形 SVM と Kneser-Ney の点数で決める。
  `-ngram=none` のときは母音の有無と子音の連続長で決める簡易判定を使う。
- **e2k** は `github.com/tenkoh/e2k-go` の `*e2k.C2K` で、入力は折り畳んだ小文字 ASCII にする
  (`café` は `cafe`、`ß` は `ss`、アポストロフィは除く)。32 文字を超える部品は e2k に渡さない。
  e2k の出力は 16 記号までで、長い語は途中で切れるからだ。
- **文字読み** は必ず成功する最後の手段だ。a から z とギリシャ文字は読み表で読む。
  折り畳んでも ASCII にならない英字 (`ə` など) は読みを持たないので、空文字列に置き換えて
  追跡情報に `drop` と記録する。英字を残さないことを読みより優先する、という方針に従う。

`acronym` には発音判定を使わない。`API` や `CLI` は発音判定を通ってしまい、アピ、クリと読まれるからだ。
単語として読む頭字語 (`NASA`、`JSON`、`SQL`) は辞書で扱う。小文字で書かれた頭字語 (`api`、`url`) は
`word` に分類されるので、同梱辞書が大文字小文字を区別せずに拾う。

形態素解析 (kagome など) は使わない。英字と日本語の境目は文字種で決まり、英単語どうしの境目は
空白、記号、数字、大文字小文字で決まる。形態素解析で新たに分かる境界がない一方で、辞書データが
数十 MB 増える。ローマ字で書かれた日本語 (`Tokyo`、`Shinkansen`) をヘボン式で読む機能を足すときに
改めて検討する。

## データの形

公開 API の中心は `Converter` と `Result` だ。

```go
type Converter struct{ /* 辞書、生成器の表 */ }

func New(opts Options) (*Converter, error)
func (c *Converter) Convert(ctx context.Context, s string) (Result, error)

type Options struct {
	Dictionaries []*dict.Dictionary // 指定順。後ほど優先度が高い
	Model        Transliterator     // nil なら e2k を使わず、word も文字読みにする
	Judge        Judge              // nil なら簡易判定
}

// Transliterator は *e2k.C2K がそのまま満たす。テストでは偽物に差し替える。
type Transliterator interface {
	ConvertContext(ctx context.Context, s string) (string, error)
}

// Judge は ASCII 小文字の語を単語として読めるかを返す。
type Judge interface{ Pronounceable(word string) bool }

type Result struct {
	Text     string
	Rewrites []Rewrite // 元の文字列での開始位置の順
}

type Rewrite struct {
	Start, End int    // 元の文字列のバイト範囲
	Source     string // 元の文字列の該当部分
	Result     string
	Method     Method // Dictionary, Model, Spell, Drop
	Class      Class  // word, acronym, letter。辞書の一致では空
	Rule       *dict.RuleRef // 辞書名とキー (または正規表現の id)。辞書の一致のときだけ
}
```

`Convert` が返すエラーは `ctx` の取り消しだけだ。e2k の失敗は文字読みへのフォールバックで吸収する。

## 守る性質とその検証

`Converter` の出力について、次の性質をテストで機械的に検証する。偽の `Transliterator` を使うので
重みがなくても走る。重みを使うテストは `YOMIKAE_C2K_MODEL` があるときだけ走る。

| 性質 | テスト |
| --- | --- |
| 出力に英字がない | 表駆動テスト、コーパス全件、`FuzzConvert` |
| 英字を含まない入力は同じバイト列で返る | `FuzzConvert` (任意のバイト列) |
| 冪等 (`Convert(Convert(s)) == Convert(s)`) | `FuzzConvert` |
| Rewrite の範囲が重ならず、`Source` が元の文字列の該当部分と一致する | `FuzzConvert` |
| 英字を返す壊れた Transliterator でも英字が残らない | 偽物を差し替えたテストと fuzz |

冪等性は最初の二つの性質から導かれる。出力に英字がなければ、二回目の変換は英字のない入力を受け取り、
何も変えないからだ。fuzz では念のため直接も確かめる。

## 分野別辞書

形式は TOML とする。一行一項目で書けて、コメントが書けて、正規表現の項目に名前付きのフィールドを持てる。
TOML はキーの重複を構文エラーにするので、同じファイル内の重複を形式が検出してくれる。
TSV は数万項目を他の資源から変換するのには向くが、正規表現の項目とファイル単位の設定を書く場所がない。

```toml
name = "tech"
license = "MIT"
case_sensitive = false # 既定。true にするとキーの大文字小文字を区別する

[literal]
GitHub = "ギットハブ"
"GitHub Actions" = "ギットハブアクションズ"
JSON = "ジェイソン"

[[regex]]
id = "semver"
pattern = 'v(\d+)\.(\d+)'
replace = "バージョン$1.$2"
```

読み込み時に次の場合をエラーにする。

- 読み (`literal` の値、`regex` の `replace` のリテラル部分) が英字を含む。
- `literal` のキーが英字を含まない。
- 大文字小文字を区別しない辞書で、折り畳むと同じになるキーが二つある。
- `regex` の `pattern` が RE2 として不正、または `replace` が存在しないキャプチャを参照する。

追跡情報の `Rule` には辞書の `name` と、リテラルならキー、正規表現なら `id` が入る。

単位 (`kg`、`MHz`) は大文字小文字で意味が変わるので、`case_sensitive = true` の別ファイルにする。

## 外部データの指定

e2k の C2K の重みは同梱しない。重みは CC-BY-SA の辞書から派生した可能性があり、
MIT のこのリポジトリには入れられないからだ。サーバー上に置いたファイルのパスを指定する。
実行中に外部と通信しない。

NGram のデータは同梱する。本家によると、学習に使ったのは CMUdict (BSD 2-Clause) と合成した頭字語だけで、
本家のコードは Unlicense だ。BSD 2-Clause は MIT と両立し、条件は著作権表示と許諾文を残すことだけだ。
そこで次のようにする。

- `ngram/data/ngram.json.gz` に gzip で圧縮して置き、`go:embed` で埋め込む。
  元の LZMA の ZIP は標準ライブラリで読めないので、展開して gzip にし直す。
  手順と元ファイルの SHA-256 は `ngram/data/README.md` に残す。
- CMUdict の著作権表示と BSD 2-Clause の全文、本家 e2k の出典を `ngram/NOTICES.md` に置く。
  バイナリにも同じ文を埋め込み、`yomikae -licenses` で表示する。BSD 2-Clause はバイナリでの再配布でも表示を求めるからだ。
- リポジトリのライセンスは MIT のままにする。
- `-ngram` を指定すると、同梱データの代わりにそのファイルを使う。`-ngram=none` で簡易判定に切り替える。

| 項目 | フラグ | 環境変数 |
| --- | --- | --- |
| C2K の重み | `-c2k` | `YOMIKAE_C2K_MODEL` |
| NGram のデータ (省略時は同梱データ) | `-ngram` | `YOMIKAE_NGRAM_MODEL` |
| 辞書 (複数) | `-dict` (繰り返し可) | `YOMIKAE_DICTS` (`:` 区切り) |
| 同梱辞書を読まない | `-no-builtin-dicts` | `YOMIKAE_NO_BUILTIN_DICTS=1` |

フラグが環境変数より優先する。辞書の一覧も同じ規則で、フラグを一つでも指定すると環境変数の一覧は使わない。
二つの一覧を混ぜると、どちらが優先度の高い辞書か分からなくなるからだ。

設定ファイルは設けない。systemd の `EnvironmentFile` や Docker の `--env-file` が同じ役割を果たし、
三つ目の指定方法は優先順位の規則を増やすだけだからだ。

重みのファイルが見つからないときは、起動時エラーで止まる。設定の誤りに起動時に気付けるからだ。
`-missing-model=spell` (環境変数 `YOMIKAE_MISSING_MODEL=spell`) を指定すると、警告を出して文字読みだけで動く。

## プロキシ

`net/http/httputil.ReverseProxy` の上に作る。

- `POST /v1/audio/speech` の本文を読み、トップレベルの `input` メンバーの文字列だけを書き換える。
  `encoding/json` の `Decoder.Token` で値の位置を見つけて差し替えるので、ほかのメンバーは順序も書式も
  元のバイト列のまま残る。`input` が複数あれば全部を書き換える。
- 本文が JSON として読めない、または `input` が文字列でないときは、書き換えずに上流へ送る。
  エラーの返し方は上流 (speech.cpp) に任せる。
- ヘッダは `Content-Length` を書き換え後の長さにする以外は変えない。`Rewrite` フックを使うので、
  `X-Forwarded-For` も足さない。
- 応答は `FlushInterval: -1` で、上流から届くたびにクライアントへ流す。SSE も `pcm` のチャンクも同じだ。
- ほかのパスとメソッドはそのまま転送する。WebSocket (`/v1/realtime`) も `ReverseProxy` の Upgrade 対応で通る。
- 書き換える本文の上限は `-max-body` (既定 1 MiB) で、超えたら 413 を返す。

## 正しさの検証と合格ライン

| 指標 | 方法 | 合格ライン |
| --- | --- | --- |
| 一次: 英字ゼロ | `yomikae stats -check` を全コーパスに掛ける。`FuzzConvert` を 10 分以上回す | 英字を含む出力が 0 件。fuzz の失敗が 0 件 |
| 二次: 前後の日本語が崩れない | `eval/asr_eval.py` で前処理あり・なしを合成し、Qwen3-ASR で書き起こす。英語の前後の日本語の文字が書き起こしに残る割合 (LCS 再現率) を比べる | 前処理ありの平均が、英語を含まない対照文の平均から 0.03 以内。再現率 0.8 未満の文の割合が対照文の 2 倍以下 |
| 三次: 読みの妥当性 | `testdata/gold.tsv` (語と許容する読みの一覧) と比べる | 許容する読みのどれかと一致する割合が 70% 以上 |
| プロキシ | speech.cpp を模したモック上流で、`input` の書き換え、ほかのメンバーとヘッダの保存、SSE の逐次転送を確かめる | 全テストが通る。モック上流が二つ目のイベントを送る前に、クライアントが一つ目を受け取れる |

二次指標の再現率は、ASR が漢字を仮名で書き起こすなどの揺れを含むので、絶対値ではなく対照文との差で判定する。
三次指標の 70% は「読みの精度はそこそこでよい」という方針から決めた。ゴールドセットの読みは人手で確認する。
